AI事業部 開発指示書 No.017

提出日：2026/08/11

件名

Otomo Fishing
日時リセット挙動改善・釣果データバックアップ／復元機能

────────────────────────────────────

【作業開始】

最初に以下のファイルを読み、内容を理解してから作業を開始してください。

docs/00-ai-development-rules.md
docs/01-fishing-log-project-rules.md

内容を理解したことを最初に報告してください。

共通ルール、プロジェクトルール、本指示書の内容に矛盾がある場合は、
実装を開始せず社長へ確認してください。

────────────────────────────────────

【背景】

No.015で新規記録日時を手動変更可能にし、
No.016で入力日時に応じて潮情報を再計算するようにしました。

実機確認の結果、
日付入力UIでリセット／クリア操作を行った場合に、
日付欄が空欄のまま残る挙動が確認されました。

また、
Otomo Fishingは現在、
釣果ログ本体を端末側のlocalStorageへ保存し、
写真の縮小コピーをIndexedDBへ保存しています。

iPhoneではSafari版とホーム画面追加版で保存領域が分かれる場合があり、
ホーム画面版の削除・再追加等によって、
それまでの釣果ログへアクセスできなくなる可能性が実機確認されました。

Otomo Fishingで最も失ってはいけないのは、
ユーザーが蓄積した釣果履歴です。

正式なクラウド同期・サーバー保存へ進む前段階として、
今回はサーバー不要のバックアップ／復元機能を実装します。

写真は今回のバックアップ対象外とします。

────────────────────────────────────

【今回の目的】

以下を実現してください。

1.
新規記録の日付入力がクリアされた場合、
空欄状態を残さず、
今日の日付と現在時刻を再設定する。

2.
日時再設定後、
その日時に対応する潮情報を再計算・再表示する。

3.
釣果ログ本体をJSONファイルとしてバックアップできるようにする。

4.
書き出したJSONバックアップから、
釣果ログ本体を安全に復元できるようにする。

5.
不正・破損・別形式のファイルを読み込んだ場合でも、
既存釣果データを破壊しない。

6.
写真データはバックアップ対象外とし、
釣果履歴本体の保護を優先する。

────────────────────────────────────

【作業範囲】

今回の対象は以下のみです。

・日付クリア時の自動再初期化
・現在時刻の再初期化
・潮情報の再評価
・釣果ログJSONバックアップ
・釣果ログJSON復元
・バックアップ形式の識別情報
・復元前の入力検証
・既存データ保護
・必要なUI追加
・必要なテスト追加
・開発完了報告書作成

サーバー、
ログイン、
クラウド同期、
写真バックアップは今回の対象外です。

────────────────────────────────────

【日付クリア／リセット時の仕様】

新規記録画面の日付入力が、
ユーザー操作またはブラウザ標準UIの操作によって空欄になった場合、
空欄状態をそのまま残さないでください。

日付欄が空になったことを検知したら、

・日付：端末ローカルの今日の日付
・時刻：端末ローカルの現在時刻

を再設定してください。

例：

変更前：
2026/08/08 05:30

日付ピッカーでクリア

期待結果：
2026/08/11 現在時刻

となること。

────────────────────────────────────

【時刻再設定】

日付がクリアされた場合は、
日付だけでなく時刻も現在時刻へ戻してください。

前回の手動入力時刻を残さないこと。

通常の時刻変更操作では、
No.015／No.016の既存仕様を維持してください。

────────────────────────────────────

【潮情報再計算】

日付クリア後に今日の日付＋現在時刻を再設定したら、
No.016の潮情報再計算処理を使用して、
その日時に対応する潮情報を再評価してください。

対応データが存在する場合：
・潮情報を再計算して表示する。

対応データが存在しない場合：
・No.016の「この日時の潮データはありません」状態を表示する。

空欄日時を基準に潮処理を行わないでください。

────────────────────────────────────

【バックアップ対象】

今回バックアップするのは、
Otomo Fishingの釣果ログ本体です。

既存localStorage内の釣果ログ構造を確認し、
現在のログ1件を復元するために必要な保存フィールドを、
原則そのまま保持してください。

対象例：

・ログID
・釣果日時
・場所
・位置情報
・魚種
・サイズ
・釣り方
・メモ
・天気情報
・潮情報
・SNS写真調整値等のログ本体に含まれる付随情報
・その他、既存ログ互換に必要なフィールド

既存ログ構造を勝手に簡略化しないでください。

────────────────────────────────────

【バックアップ対象外】

以下は今回バックアップしないでください。

・IndexedDB内の写真バイナリ
・元写真
・SNSカード画像
・キャッシュ
・ブラウザ設定
・アプリアイコン
・潮データファイル
・天気APIレスポンスキャッシュ
・その他、釣果ログ本体以外の不要な端末データ

────────────────────────────────────

【写真参照の扱い】

既存ログにphotoId等の写真参照情報が含まれている場合、
バックアップJSON内にログ本体の互換情報として残すことは可能です。

ただし、
写真バイナリ自体は書き出さないでください。

復元先端末に対応する写真データが存在しない場合でも、
釣果ログ本体の復元を失敗させないでください。

写真参照先が存在しない場合は、
既存の写真なし状態として安全に扱えるようにしてください。

写真欠損を理由に、
釣果ログ全体を削除・拒否しないこと。

────────────────────────────────────

【バックアップ形式】

バックアップはUTF-8のJSONファイルとして出力してください。

ファイルには、
単なるログ配列だけでなく、
Otomo Fishing用バックアップであることを識別できる
最小限のメタ情報を含めてください。

推奨構造例：

{
  "app": "Otomo Fishing",
  "format": "otomo-fishing-backup",
  "version": 1,
  "exportedAt": "...",
  "logs": [...]
}

具体的なキー名は、
既存コードとの整合性を確認したうえで最小限調整して構いません。

ただし、
復元時に別JSONファイルと区別できる識別情報を必ず持たせてください。

────────────────────────────────────

【バックアップファイル名】

ユーザーが判別しやすいファイル名としてください。

例：

otomo-fishing-backup-20260811-2310.json

日時部分はバックアップ実行時のローカル日時を使用してください。

Windows／iOS等で問題になる記号は使用しないでください。

────────────────────────────────────

【バックアップ操作】

ユーザーが明示的に操作して、
JSONファイルを書き出せるUIを追加してください。

例：

「バックアップを書き出す」

または同等の意味が明確な名称。

実装方式は、
現在のブラウザ互換性を考慮して最小限で採用してください。

Web Share APIを利用する場合でも、
ファイル保存できない環境向けのフォールバックを用意してください。

ただし、
今回の主目的は確実にJSONファイルをユーザー側へ渡せることです。

────────────────────────────────────

【復元操作】

ユーザーがバックアップJSONファイルを選択し、
復元できるUIを追加してください。

例：

「バックアップから復元」

復元ファイル選択後、
いきなり既存データを書き換えないでください。

必ず検証を先に行ってください。

────────────────────────────────────

【復元前検証】

復元前に最低限以下を検証してください。

・JSONとして解析可能
・Otomo Fishing用バックアップ形式である
・format識別子が一致
・versionが対応範囲
・logsが配列
・各ログが最低限の構造を持つ
・危険な型崩れがない

検証に失敗した場合は、
既存データへ一切変更を加えず、
ユーザーへ読み込み失敗を表示してください。

────────────────────────────────────

【復元方式】

Version 1では、
既存データを無条件に全削除して置き換える方式は禁止します。

既存ログを守るため、
安全な統合方式を採用してください。

基本方針：

・同一ログIDが既に存在する場合は重複登録しない
・存在しないログIDだけ追加する
・既存ログは勝手に削除しない
・既存ログをバックアップ側の古い値で勝手に上書きしない
・復元後は既存の新しい順表示仕様に整合させる

同一IDで内容が異なる場合は、
Version 1では既存端末側データを優先してください。

競合解決UIの追加は今回不要です。

────────────────────────────────────

【ログIDがない旧データ】

既存アプリの過去ログにIDなしデータが存在し得る場合は、
既存コードを確認してください。

IDなしログを安全に扱うための既存互換処理がある場合は利用してください。

新たな推測で大量のID再生成を行わないでください。

必要な場合は、
既存仕様と最小限整合する方式を採用し、
報告書に明記してください。

────────────────────────────────────

【復元結果表示】

復元完了後、
ユーザーが結果を理解できるよう、
最低限以下を表示してください。

例：

「3件の釣果を復元しました」

または、

「復元できる新しい釣果はありませんでした」

エラーの場合：

「バックアップファイルを読み込めませんでした」

など、
状態が明確な文言としてください。

────────────────────────────────────

【復元後の表示】

復元成功後は、
釣果一覧へ復元データを反映してください。

アプリ再読み込みを必須にしないことが望ましいですが、
既存構造上最小変更で安全に実装するために
再描画処理を利用してください。

復元処理によって、
入力中の新規記録データを不要に消さないよう注意してください。

────────────────────────────────────

【localStorageの扱い】

既存localStorage保存キー・ログ構造を確認し、
互換性を維持してください。

以下は禁止します。

・localStorage全体のclear()
・Otomo Fishing以外のキー削除
・復元前の既存ログ全削除
・破損ファイル読み込み時の初期化

復元処理は、
検証完了後にのみ必要な書き込みを行ってください。

────────────────────────────────────

【IndexedDBの扱い】

今回、
IndexedDB内の写真データは変更しないでください。

以下は禁止します。

・IndexedDB全削除
・既存写真の削除
・復元処理に伴う写真ストア初期化
・バックアップ用写真書き出し

復元ログのphotoIdが端末内に存在しない場合でも、
安全にログを表示できることを優先してください。

────────────────────────────────────

【UI】

既存デザインを大きく変更しないでください。

バックアップ／復元操作は、
既存の主要入力導線を邪魔しない場所へ配置してください。

スマートフォン優先で、
誤操作しにくいUIにしてください。

復元はデータへ影響する操作のため、
ファイル選択後に内容検証してから実行してください。

必要に応じて、
簡潔な確認文を表示して構いません。

────────────────────────────────────

────────────────────────────────────

【セキュリティ・安全性】

バックアップJSONの内容をHTMLとして直接描画しないでください。

復元ファイル内文字列を使用する場合は、
既存の安全な描画方式を維持してください。

ファイル内容に想定外のプロパティが含まれていても、
アプリ実行コードとして評価しないでください。

eval等は禁止します。

────────────────────────────────────

【AIの裁量】

以下は既存コードを確認したうえで、
最小限の変更で最適な方式を採用して構いません。

・バックアップ／復元UIの配置

既存ログ保護を最優先してください。
